### 候选 B 不通过的原因（概述）

在我们测试的这一版本和这组配置下，候选 B 的服务端没有把“谁在调用”与“读谁的消息、以谁的名义发送”可靠地绑定在一起，因此第 2、3、4、9 项的隔离要求无法只靠配置满足；第 5 项在私聊上也存在可绕过的路径。

具体的请求细节和复现步骤没有写进这个公开仓库：我们尚未向上游报告，复现脚本只保留在本机（`openim/` 目录不入库）。以上只是这一版本、这组配置下的观察，不代表其他版本，也不构成对该项目的整体评价。

补法都要求浏览器不能直接连 OpenIM 的网关和接口：要么改服务端源码加校验并自行维护分支，要么在前面加一层理解其协议的代理。两者都相当于重做一部分消息通道，与"优先复用"的目标相悖。按清单约定，B 的第 10 项不再做。

### 候选 A 需要说明的地方

- 第 3 项原生行为：任何已登录用户知道地址就能下载附件。补法是入口处封掉直接下载，附件改由规则服务代取，判断依据是"调用者自己能否读到携带该附件的那条消息"，直接复用 Synapse 的历史边界。头像和缩略图需要另行处理，本次未做。
- 后加入者调用 `timestamp_to_event` 能拿到一条旧消息的编号，但读不到内容。
- 房间只能由 Agent Family 服务代建；成员不能自行建房、邀请、踢人、改权限或开启加密。这是本次设定的策略，也是模块里写死的。
- 规则服务是硬依赖：它不可用时所有发送都会被拒绝。正式实现需要考虑它的可用性。
- 已读回执、正在输入、个人资料修改不经过这个模块。

### 第 10 项：当前界面接真实数据（候选 A）

`ui-live/` 是 `prototype-v2` 的副本。访问 `/?live=<服务器地址>` 时改用真实会话，不带参数时仍是原来的模拟数据。

- 新增 2 个文件共 215 行（`src/live/matrix.js`、`src/live/LiveStore.jsx`），改动原有文件 3 处共约 8 行。页面组件和样式没有改。
- 浏览器实测：登录；会话列表、未读数、四种会话类型的标题和主人标注正确显示；发送成功；另一位真人和 Agent 的消息实时出现；房间冻结后发送被服务器拒绝，界面沿用原型已有的"发送失败，未发布"样式。截图：`results/a-ui-live-frozen-send.jpg`。
- 遇到的障碍：
  - 原型把"我"写死为 `me`，人物表是模块级常量。验证里靠运行时改写绕过，正式接入要改成从会话身份读取。
  - 原型没有"纯真人群"类型，验证里暂归为混合群。
  - Agent 的主人归属本次放在房间状态里；正式实现应来自规则服务。
  - 附件、图片、引用回复、冻结状态横幅、扩员和恢复流程未接。
  - 打包体积从 383 KB 增到 1428 KB（gzip 后约 419 KB），未做拆分。

### 独立攻击测试发现的问题（候选 C）

服务端和测试都是同一个作者写的，所以另请独立审查者专门攻击，脚本在 `core/adversarial/`。**核心规则大多守住了，但找到了实在的漏洞**：

守住的：非成员访问（且无法探测会话是否存在）、服务端接口、入群批准、后加入者与重新入群的历史边界、长连接推送、附件、身份冒充。

没守住的：

1. 一个畸形地址的请求就能让进程退出，不需要登录。
2. 任意已登录用户发一个不合规的长连接数据帧就能让进程退出。
3. **规则漏洞：主人自己退出会话后，他的 Agent 还留在里面**，主人随后看不到该会话。
4. 上传到一半时会话被冻结，上传仍然成功。
5. 冻结期间退出会话仍会写入一条系统消息。
6. 重发标识在不同会话间重复使用时，第二条消息被静默丢弃。
7. 登录耗时能分辨账号是否存在；没有限速。
8. 同步游标是全局计数，无关的人能看出全站有新消息；后加入者能看出入群前有多少条消息。
9. 批准不会过期，被移除后旧批准仍可用。
10. 多种畸形参数导致 500（进程不退出）。

另有设计上的空白：没有退出登录和凭据吊销、上传文件类型未限制、角色“旁观”未限制发言和邀请（本次有意如此）。

这些正是自己做的代价：Synapse 多年来已经踩过并修掉了这一类问题，自己做就要自己负责。其中 1、2、10 属于手写网络层的问题，正式实现使用成熟框架和参数校验即可避免；3、4、5、6、9 是规则与边界问题，需要逐条设计并用对抗测试守住。验证版没有逐一修复。

需要同时说明：在候选 A 下，账号、好友、规则裁决、附件代取仍然是我们自己写的服务，同样会有这一类问题；差别只在“消息收发这一段”是否由 Synapse 兜住。

### 并排比较

| | A：Synapse＋规则模块 | C：自研核心 |
|---|---|---|
| 运行的部件 | Synapse、规则模块、AF 服务、入口代理、两个数据库 | AF 服务（含消息）、一个数据库 |
| 权威数据 | 成员名单两处各存一份，需保持一致 | 只有一处 |
| 规则生效方式 | Synapse 每次写入回头询问 AF 服务；询问不到就全站不能发言 | 同一事务内判断并写入 |
| 规则模块管不到的地方 | 已读、正在输入、个人资料、附件下载、搜索 | 无，接口只有我们写的那些 |
| 重新入群 | 能看到以前在群时段的消息 | 可按产品规则定义 |
| Agent 身份与外部接入 | 需在 Synapse 的机器人机制之外另做 | 与消息通道是同一套 |
| 自定义消息（任务卡、授权申请） | 塞进 Matrix 的消息格式 | 原生 |
| 浏览器包体积 | 多约 1 MB | 多约 4 KB |
| 消息通道的成熟度 | 高，多年生产使用 | 从零开始，需自己做对并长期守住 |
| 原生端与推送 | 有现成 SDK 和推送网关 | 需自己做 |
| 将来跨服互通 | 打开联邦即可起步 | 需另写桥接 |
| 许可证 | Synapse 为 AGPL（只部署不改） | 完全自主 |

未测：真实 Postgres 下的并发（PGlite 是单连接，并发测试结论有限）、大量会话与长历史下的性能、断线重连的各种边界、多设备已读同步、手机端。
