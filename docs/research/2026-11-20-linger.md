# Linger (simplexai-labs/linger): what we can learn from it

Researched 2026-11-20 from the public repo (README, `docs/`, `AGENTS.md`, selected source files on GitHub raw). Mechanisms are described in my own words. Nothing was cloned or run. Where a page was read through a summarising fetch tool rather than line by line, treat numbers as "as reported"; the numbers marked (code) were read from source files, the ones marked (doc) from `docs/*.md`.

## Summary (10 lines)

1. What it is: a local-first personal agent platform. A Go server (TeamHub, PostgreSQL + River jobs) owns Rooms, tasks, permissions; a Node service runs agents, memory and wiki; a per-computer Go daemon runs the model runtimes (Codex, Claude Code, Pi, Antigravity) and desktop/browser control.
2. License caveat: modified Apache 2.0. Forbids offering it to third parties as a hosted or multi-tenant service without written permission, and requires keeping the logo in the frontend. Agent Family is hosted, so: ideas only, no code, no prompt text.
3. Ranked idea 1: Dreaming = a tiny, versioned rule list (max 20 rules, 200 chars each) plus a separate "clues" list (max 20, expire after 14 days) that carries weak evidence from night to night; two same-kind clues become a rule, and each version keeps a change note for rollback.
4. Ranked idea 2: a priority queue per model endpoint with adaptive concurrency (rises when fast, halves on rate-limit) and pre-emption of background work by chat; plus "background model calls are cancelled and re-queued, not failed".
5. Ranked idea 3: memory with hard shapes and an app-written change log: summaries capped at 3,000 chars, lists at 20 entries of 500 chars, entry IDs so updates touch only named entries, every fact cites its source, the model proposes edits section by section and code checks each against what it replaces.
6. Ranked idea 4: a separate judge for tool actions ("permission review") that grades risk and how clearly the owner authorised it, only the owner's own words count as authorisation, other people/agents/web text are context only; high risk without authorisation becomes an approval card that expires after 10 minutes.
7. Ranked idea 5: a quiet delivery queue for unasked messages: they wait until the chat has been quiet 3 minutes, are sent in order as one batch, and are dropped if the thing that justified them was revoked; plus quiet hours and a daily cap stated in the skill text.
8. Also useful: team.md as a validated, size-capped plan file (64 KiB, 50 members, 5 named patterns, parse errors reported all at once); background task states (running / idle / waiting_for_approval / failed / canceled) with "canceled keeps files and session"; idempotency keys on every agent write.
9. Does not transfer: everything that assumes one owner (memory is "your" memory, one trust domain, no privacy between people), no cost control for a hosted wallet (model cost falls on each user's own endpoint or key), no abuse model, no reactions-to-learning, hearsay/room privacy.
10. Weak spots: team loop and cost limits, task time/step/cost limits, crash recovery of tasks, onboarding text, and "routines" limits are thin or absent in the public docs (details below, marked unconfirmed). Linger's "5 reminders a day / quiet hours 22:00-08:00" appear in the docs, but I did not find them enforced in the Go code I read.

## Vocabulary map

Room = chat; Another Me = the owner's main agent in their direct room; Meta = the agent you talk to in a Room; AlterEgo = a background copy of an agent for one Task; Tracking Item = a todo/question/meeting the agent follows; Routine = a scheduled wake attached to a tracking item; Run = one model turn-set; Operation = a unit that holds one model slot; Computer = the user's machine with the daemon; Context = one agent in one Room/Task/Document (one workspace each).

## 1. Memory and wiki

What is stored (doc, `docs/wiki-and-memory.md`): two separate things.

- Personal wiki: typed Markdown pages (client, contact, project, topic, session); one page per real entity; each meeting becomes a session page linking the entities it touched. Built from mail, chat, meetings, files, agent chats.
- Per-agent memory: preferences, proven procedures, decisions, environment facts, lessons from failures. Explicitly excludes progress notes, generic advice, secrets, guesses. Carries across Rooms, not across agents. Lives as read-only files inside every workspace of that agent: a short index (`summary.md`), a topic-organised `MEMORY.md`, and one summary file per conversation.

Shape: pages and files, not embeddings. Summary sections up to 3,000 chars; list sections up to 20 entries of 500 chars, each entry with an app-assigned ID so an update changes only the entries it names. Facts cite the message or file version they came from; a rewrite must keep old sources or say why one was dropped. A Change Log (written by the app, not the model) keeps one dated line per rewrite/edit/retraction/merge, newest 20.

Nightly/background pass: wiki sources are read, a model proposes section-level changes, the app checks each proposal against the page it would replace. Agent memory has two stages: extraction after every 5 successful runs (new messages and tool calls become a session summary plus candidate memories), and consolidation after 6 hours without a run or on context compaction (merges candidates, drops duplicates and disproven facts, waits until the agent is idle; early merge at 64 KB or 30 conversations). Both are tool-free model calls on the agent's own computer. Scheduler (code, `apps/node-services/src/memory/scheduler.ts`): hourly wiki update; at local midnight a daily report (waits for the midnight wiki task), weekly report on a set weekday (waits for the daily); per-subject serial lanes; missed hours are replayed on catch-up but only midnight slots; up to 6 attempts with delays 15 s, 1 min, 3 min, 10 min, 1 h; if the computer is offline it retries every 5 min without using an attempt and gives up after 7 days; state is saved before and after each task.

Search (doc): command `teamhub knowledge`, server limits results to the person the agent works for. Two ranked lists: wiki pages and daily/weekly reports (overview), and original messages/transcripts/documents/emails (exact detail), plus a facts list. Uses PostgreSQL full-text keyword search for the query plus up to six alternate wordings, a time hint boosts but never hides, merged by reciprocal rank fusion. Says there is no embedding or reranker model. Rule given to agents: search originals before saying something was never recorded. For harder questions, agents also check live sources. Recall into a session: only the short index goes in as a hidden note on the first message of a session (or after compaction); the rest is read on demand; memory never goes into the system prompt.

Conflicts / duplicates / staleness: summary rewrites need a stated reason; list entries change one at a time and retractions are logged; overfull lists merge their oldest entries into one dated entry; facts that can change (dates, roles, amounts) are re-checked against the latest source before being presented as current; disproven facts removed from agent memory.

User view/correction: the wiki and agent memory are read-only files for the agent; the Change Log shows history. I found no direct edit UI in the docs: unconfirmed whether the web app lets the user edit pages (the web app has a Wiki area per `docs/architecture.md`). Corrections seem to happen by telling an agent.

Privacy tiers: none described. Only boundaries: search limited to the registered person's knowledge; agent memory limited to that agent; only Room conversations feed agent memory (delegated tasks and document work do not).

Sources: https://github.com/simplexai-labs/linger/blob/main/docs/wiki-and-memory.md ; `apps/node-services/src/memory/scheduler.ts`; `apps/node-services/src/memory/README.md` (named, not read in full).

What Agent Family could take: hard size caps plus entry IDs plus an app-written change log plus "every fact cites its source" for the three memory rooms; and the idle-triggered consolidation (6 h quiet or 30 conversations) as a trigger for 入梦 in addition to the clock.

## 2. Dreaming and proactive self-improvement

Signals (doc `docs/proactive.md`, code `apps/node-services/src/memory/proactive-dreaming.ts`, prompt `apps/node-services/prompts/memory/proactive/dreaming.md`): each night, after that person's daily report, one model call reads each message the agent sent unasked (tagged with what woke it: review, routine, event or plan) together with the next ~20 room messages, each reply cut to 1,000 chars. "Landed" is judged by the model from those replies, not by a button. Counts as a signal only: the user saying how to handle a kind of thing, the user acting on or closely discussing the reminded matter, or the user commenting on timing. Does not count: opinions on content, silence, unrelated messages, one-item outcomes, plain agreement. The reactions feature (emoji) is explicitly not wired to learning (code, `messagereaction.go`).

Representation (code): a "guideline" row with a version number, a list of rules (strings), and a list of clues, in table `memory_source.proactive_guidelines`, one row per version with a change note up to 2,000 chars; old versions kept for rollback, only the newest is read. Limits: 20 rules (1 to 200 chars each), 20 clues. A clue has: matter (<=120 chars), kind (<=60), optional time window (<=40), a leaning (remind directly / track for follow-up / stay silent), a seen count and last-seen date. Rule shape in the prompt: kind of thing[, time window] -> one of three decisions.

Add / change / remove: the model returns the kept rules, kept clues, a list of removed rules and a change note, in a JSON schema (no extra fields, bounded lengths). Code then trims, dedupes and caps: new rules first, then surviving old ones; oldest fall off beyond 20; one clue per (matter, kind) with newest winning; clues sorted newest first; malformed or future dates set to today. Version +1 each run even if unchanged. Clues expire 14 days after last seen; rules have no time expiry.

Anti-overfitting ("push back twice"): per the prompt, clues of the same kind and leaning are promoted to a rule when their combined seen count reaches 2; a rule is created at once only if the user names the kind ("from now on", "this kind"); two or more turned-down items in one area give a stay-silent rule for that area. The code itself sets no threshold: the model applies it, the code only counts. Contradicting feedback replaces a clue and removes or narrows a rule; same-direction rules merge; tracking vs silence feedback in one area stay separate unless the user clearly wants the whole area silent; "too late at night" never turns into silence, only into "follow up later in that window". A night without feedback changes nothing. A rule is written only if it would change the default decision. Failure safety: if the model call or save fails, the day's exchanges are not cleared and are reprocessed next night.

User inspection/override: the docs do not describe it (unconfirmed). The user can state a rule in chat and the next pass writes it. Rules live in a database table with versions, so rollback exists at the data level; no UI seen.

Gating of proactive sends: (doc) quiet hours 22:00-08:00 and a cap of five reminders a day mean events are only recorded, not sent; one item in one state is judged once a day; delivery waits until the chat has been quiet 3 minutes. (code, `reminder/quiet_wake.go`, `proactive/window.go`) the 3-minute quiet window and a 10-attempt delivery job are confirmed; I did not find quiet hours, a daily cap or dedup enforced in the files I read (they may live elsewhere), so the 22:00-08:00 and "five a day" numbers are doc-only (unconfirmed in code). Review windows: only after 20 unjudged messages in the owner's direct room; the first time a room is seen, history is skipped; the progress marker advances only if unchanged (compare-and-set), so two reviews cannot judge the same window. The proactive skill text (`skills/builtin/proactive-response`) tells the agent to tell only if the owner would act or want to know now, to recheck facts that may have changed, to send at most one short message conclusion-first, to stay silent with no filler, to avoid 22:00-08:00 for routines unless urgent, and never to pass on another person's private matters.

Sources: https://github.com/simplexai-labs/linger/blob/main/docs/proactive.md ; the three paths above.

What Agent Family could take: for the feedback system, copy the two-tier idea (weak "clues" with seen-count and 14-day expiry, strong "rules" promoted at seen >= 2 or when the owner names it), a hard cap on rule count with merge-before-drop, and version rows with change notes so any night's edit can be rolled back.

## 3. Agent teams

team.md (code `apps/teamhub/internal/teammd/document.go`; doc `docs/team-md.md`; skill `skills/builtin/collaborate`): a Markdown protocol published into a Room by an orchestrator. One frontmatter key `collaborate_pattern`, one of five values: classify-and-act, fan-out-and-synthesize, adversarial-verification, tournament, loop-until-done. Three required sections: Task Goal (<=4,000 bytes), Orchestrator (exactly one agent), Team Member (1 to 50). Each agent has a unique name, an Actor ID, optional Role (<=1,000 bytes), and "Report to" / "Receive from" lists (<=20 names, must name participants in the same document). Whole document <=64 KiB, UTF-8. The parser reports all structural errors at once with path, code, message. Room check: every Actor ID must be an active member of the Room. The server stores the text unchanged; each publish replaces the whole file and bumps a revision number.

Choosing/creating agents: the orchestrating agent looks at the agents already in the Room; missing ones must be added first, either invited by Actor ID or created with a name and working instructions. If the sponsor (owner) is in the Room these take effect immediately; otherwise invitations are refused and new agents wait for sponsor approval (there is an `agentcreationapproval` package). Publishing never adds anyone.

Coordination: publishing notifies every declared participant except the publisher with one mention. Entry agents (those that receive from the orchestrator) start at once; downstream agents wait for a hand-off message; an agent with two upstreams waits until both arrived. The file is the shared state. Reporting lines are declarations only: the server does not enforce them, deviations must be stated in chat. Turn-taking beyond "wait for your upstream" is not specified.

Loops and runaway cost: none found in the docs, the skill, the parser or `taskexecution/coordinator_progress.go` (read-only status snapshot). No round limit even for the loop-until-done pattern. Unconfirmed whether any enforcement exists elsewhere. User watching/stopping a team: not described; team members are normal agents in a Room, so the user sees their messages (inference, unconfirmed).

What Agent Family could take: the plan-file idea (small, validated, size-capped, replace-whole, revisioned; names and IDs must be real room members; errors listed all at once), and the named patterns as a small closed list. Add what Linger lacks: a hard turn/budget cap per team run.

## 4. Task delegation (background copies)

Mechanism (doc `docs/task-delegation.md`, code `apps/teamhub/internal/taskexecution`, `taskdelegation`): the Meta (the only agent that talks to the owner, one per Room) starts an AlterEgo, a background copy with its own session and workspace, for each Task; tasks run side by side while chat goes on. Only the Task folder is linked into both. An AlterEgo never talks to the owner, never asks questions (questions go into its report and the Meta decides whether to ask), and cannot start or stop tasks. Up to 10 concurrent tasks per agent. It can read other tasks' folders in the same Room but needs approval to edit them.

Progress: each task is one activity line (name + state); opening it shows a chat-like view: brief, follow-ups, every step (command, file, search), replies, approval cards. Asking "how is it going" only reads status. Coordinator status snapshot lists running/waiting tasks with time in state, pending approvals, last report time, latest step.

Results: when a turn ends the task goes `idle` and the Meta is woken with the last reply; result also appears in chat as a card; files land in the Meta's workspace under `playground/<task-id>/`. States: running, idle, waiting_for_approval (nobody woken until answered), failed (Meta woken with the error), canceled.

Cancellation: ask the Meta, or a cancel button in the background-tasks list, or inside the task view; canceled keeps files and session and can be resumed by the next request. Follow-ups can be added while it runs (run now or queue behind the turn).

Limits: concurrency 10 and an approval window of 10 minutes (doc). Each attempt has a stored deadline: past it the attempt stops with a time-limit failure, queued runs are cancelled, session kept (code); the deadline value is not visible in what I read. Step and cost limits: none found (unconfirmed they do not exist). Reconciliation reads state from PostgreSQL each time, uses revision numbers to detect conflicts, and never auto-retries: a new attempt starts only when the Meta sends a message or an approval arrives (code). Restart/crash: docs say nothing about tasks; the architecture doc says the daemon's event ledger (SQLite) replays after reconnect, every agent write carries an operation ID so a retry returns the stored result and an unknown outcome is reported not re-sent, and desktop input with unknown result blocks its lane. Self-hosting doc: stopping node-services requeues in-progress replies rather than failing them.

What Agent Family could take: the state set, the rule that a background copy never talks to the owner (it reports to the main agent, which decides whether to bother the owner), "canceled = paused, keep everything", and idempotency keys on every write so a crash can be retried safely. Add the per-task budget Linger lacks.

## 5. Model scheduling / concurrency

Doc `docs/model-scheduling.md` (only the doc was read; the implementation is in the daemon, not located; implementation details unconfirmed).

- One queue per model endpoint; all work on a computer that uses that endpoint shares it.
- Concurrency starts at 1 and grows to at most 8 for gateway/key endpoints (or unknown), fixed 10 for runtimes whose models are all on the user's own account.
- Adaptive limit: +1 when work waits and latency per 1,000 new prompt tokens stays near the single-job speed; -1 when clearly slower; halves and holds for 1 minute on rate-limit/overload/timeout refusal; a limit it dropped from is not retried for 5 minutes, doubling up to 30 minutes if the retry is slow too.
- Soft limit = hard limit minus 1 (min 1) for ordinary work; recordings' questions/notes, chat and standalone approvals may use the last slot.
- Priority (high to low): tool approval (borrows the reviewed run's slot), recording questions and notes, chat, tasks and documents, scheduled/proactive work (routines, proactive runs, auto follow-ups), compaction, background (agent memory, user memory, profile, insights, wiki refresh). Equal priority: arrival order. Merged inputs take the highest priority among them.
- Pre-emption: when chat-or-higher work is first in line and cannot start, it displaces the lowest-priority running work one unit at a time. Background model calls are stopped first (stop confirmed, call re-queued at its priority, retried as the same attempt, not counted as failure). Otherwise it asks the lowest-priority running run below it to yield; a run can yield only if its runtime has a resumable native session (and has produced output or a tool event); it keeps its ID and status and resumes in the same session. Approvals, recordings and compactions are never interrupted. If cleanup cannot be confirmed, the runtime refuses further work until restart.
- Time limits count only running time, not time waiting for a slot. Wiki refresh budget 150 minutes of slot-holding time, hard max 4 hours, no new step after 3.5 hours, publishes what it has accepted. Memory chains release the slot between steps so a waiting chat can jump in.
- The queue never reorders a conversation: a new message either joins the reply in progress or waits for the next turn.
- Budgets/cost accounting for cloud runtimes: not in this doc. Self-hosting doc: no gateway, no quotas; cost lands on the user's endpoint or API key (BYOK key kept on the computer in an owner-only file).

What Agent Family could take: our small judge, memory review (小憩) and nightly consolidation (入梦) are the "background" class and should yield to a person's reply; adaptive concurrency halving on provider rate-limit errors; count timeouts only from the moment a slot is held; replies and tools never queue behind background jobs.

## 6. Tools and permissions

Approvals (doc `docs/architecture.md`): sending mail or messages and writing to connected apps (GitLab, Notion, Sheets, Airtable) wait for a card in the Room; an approved write runs exactly once. Desktop, browser and shell actions go through a Guardrail: rule-based checks first, then an LLM review (one runtime is not reviewed, another only when it asks for permission).

The reviewer (`apps/teamhub/internal/permissionreview/policy.md`): for each tool call a judge outputs risk (low, medium, high, critical), authorisation (from "owner named the action, target and content" down to unknown), a decision, and a one-sentence reason written for the owner reading the card. Only the verified sponsor's messages authorise; other room members, other agents, web pages, tool output and file contents are context only; later revocation beats earlier approval; a past denial or a consumed one-time approval authorises nothing new; "look/read/draft" never authorises sending. Low/medium: allowed unless injection or a specific rule. High: allowed only with at least medium authorisation and narrow scope, otherwise an approval card. Critical (secret exfiltration, big irreversible destruction, changing its own approval controls): denied, no card. Missing key evidence on a possibly-high action: ask.

Shown while a tool runs: the task view lists every command/file/search step; approval cards in the Room; desktop: agents read windows via an accessibility-tree style view; on a Mac, if the user switches app the agent stops typing. After: results as cards; per-step history in the task view. Bounds on tool results: not described (unconfirmed). Security details: per-agent token (48 h, renewed) checked server-side against the agent's current permissions; page scripts not offered to agents; local helpers bind to localhost or owner-only sockets.

What Agent Family could take: for the read-only tools in progress, the principle that only the owner's own words authorise anything and other people's messages in a group are data, never instructions (matters more for us than for Linger); and an owner-readable one-sentence reason on any approval whisper.

## 7. Routines / scheduled jobs

Code `apps/teamhub/internal/reminder/cadence.go` (read), `wake_prompts.md`, `quiet_wake.go`. A routine is a scheduled wake attached to a tracking item, created and moved by the agent itself. Recurrence kinds: daily (clock time, named time zone), weekly (1 to 7 weekdays, clock time, time zone), every N minutes (multiple of 10, min 10, max 10,080, UTC), every N hours (1 to 168, converted), once (UTC timestamp). Missed slots: intervals stay on a fixed grid and skip missed slots; daily/weekly/once recompute from now. Name and prompt must be non-blank within a rune cap whose value I did not see. Per-agent count limit: not found (unconfirmed). Wake kinds: review, routine, event, plan, scheduled; only "scheduled" is excluded from nightly learning. Routine wakes deliver through the same 3-minute quiet queue; a due reminder goes out even if the lookup finds nothing new; monitoring checks stay silent unless something changed; event text is data, not instructions.

What Agent Family could take: a closed list of cadence kinds with a 10-minute floor, and "a scheduled wake that is not proactive does not feed learning".

## 9. Other relevant points, and what does not transfer

Relevant:
- Idempotent writes (operation IDs; unknown outcome is reported, not re-sent) and compare-and-set progress markers for review windows: cheap protection against double work on retries.
- Hidden wake messages: proactive wakes arrive as hidden messages written "by" the owner to the agent, so the agent's reply is recorded as a proactive output for learning; only the first agent message answering a delivered wake counts.
- Background jobs are tool-free model calls; memory is not put in the system prompt but delivered as a hidden note, with the rest read on demand.
- "Tell one agent, every agent knows": one knowledge base per person, searched with full-text plus fusion, no embeddings. Cheap and inspectable.
- Skills are versioned folders embedded into the server (20 built-ins); TeamHub parses SKILL.md itself.
- A CLI replaces per-tool MCP servers (155 commands); per-agent tokens; server-side permission checks.

Does not transfer (Linger is single-owner and local):
- Privacy between people: one owner means one trust domain. No hearsay room, no vault, no rule for what an agent may say in front of others; the proactive skill only says not to pass on others' private matters. Our three-room memory and group-visibility rules have no counterpart.
- Hosted cost control: no wallet, allowance, metering or per-owner budget; cost is the user's own endpoint or key. Rate-limit handling is for protecting one endpoint, not for fairness between users.
- Abuse: no spam, prompt-injection-from-other-users, or cross-user rate limiting beyond treating event/web text as data. Multi-user self-hosting exists (one owner account, LAN) but the docs do not describe data separation between users.
- Local-model machinery (GPU expert paging, hardware planner) and desktop/browser control tied to the user's own machine.
- Social behaviour between users' agents: not covered. The team feature is agents of one owner in one Room.
- No feedback buttons: emoji reactions do not feed learning; learning is only from free-text replies read by a model.
