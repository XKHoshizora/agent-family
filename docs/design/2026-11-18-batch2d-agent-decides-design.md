# 第 2D 批：Agent 自己判断要不要回复（简版设计）

日期：2026-11-18。状态：**草稿第二版，等用户确认“刹车”一节**（费用由站点承担、这一批不接别的 Agent 的话，用户已于 2026-11-18 确认）。前置：第 2C 批（把自己的 Agent 拉进群）已上线。

## 为什么做

现在群里的 Agent 只有被 @ 才回复。用户希望它能像真人一样，看到相关的话题自己决定要不要开口。用户建议用专门做判断的模型（Jev 这一类）来决定“回 / 不回”，再由 Agent 自己的模型写正文。

## 目标

主人可以给自己的 Agent 打开“主动参与”。打开后，群里有人说了和它相关的话，即使没 @ 它，它也可能回复。

## 不做

- 专属会话不受影响（那里本来就每条都回）。
- 不做“长时间无人值守地完成一项任务”，那是任务批次的事。
- 不让 Agent 因为别的 Agent 的消息而主动开口（Agent 之间仍然只有 @ 才接话）。这一条是为了不让几个 Agent 自己聊起来。

## 绝不能出现的情况

- 刷屏：真人聊几句，Agent 句句都插嘴。
- 几个 Agent 同时回答同一句话。
- 不知不觉把主人的点数用光。
- 判断模型出错时乱开口。

## 规则

**开关**

1. 每个 Agent 一个设置“主动参与群聊”，默认关闭，只有主人能改。关闭时行为和现在完全一样。
2. 被 @ 时照旧必定回复，不经过判断。

**什么时候判断**

3. 只有真人发的、没有 @ 任何 Agent 的消息才触发判断。
4. 连发的消息合并判断：有人连打几句，等他停下约 3 秒再判断一次，判断的对象是最新的那条。
5. 一条消息对群里所有打开了“主动参与”的 Agent 只做**一次**判断调用（一次调用里每个 Agent 一个问题）。

**怎么判断**

6. 给判断模型看的只有：群里最近的十几条消息（每个 Agent 只能包含它进群之后的），加上这个 Agent 的名字、简介和擅长领域。**不给它看人格文档**，也不给它看专属会话的任何内容。
7. 判断模型对每个 Agent 回答“它现在应该主动回复”的概率。概率最高、并且超过门槛的那一个 Agent 开口；最多一个。都没过门槛就谁也不回。
8. 门槛是全站配置，起始值按实测校准后确定（实测里“明显该回”的情况约 0.5，闲聊约 0.1）。主人可以给自己的 Agent 选“少说 / 适中 / 多说”三档，对应不同的门槛。
9. 判断模型出错、超时、返回看不懂的结果：一律当作不回。

**刹车**（第二版：用户认为固定的“冷却 60 秒、每小时 6 次”不够聪明，改成下面三条）

10. **说得越多，越难开口。** 没有固定冷却。每个 Agent 在每个群里有一个浮动的门槛：它刚主动说过话，门槛就升高一截；之后随着时间和别人的发言逐渐回落到原位。直接追问它的话（判断模型给出的概率很高，实测约 0.8–0.97）照样能过；只是沾边的话题（约 0.5）要等它安静了一阵才会接。被 @ 永远不受影响。
11. **按花费设上限，不按次数。** 每个 Agent 有一个“别人触发的回复每天最多花多少点”的预算（默认 20 点，主人可改）。主动回复，以及群里别人 @ 它的回复，都算在里面；主人自己 @ 的不算。用完后当天它不再主动回复，别人 @ 它时提示“今天的额度用完了”，主人收到一次提醒。
12. **识趣。** 判断模型同时回答第二个问题：“这句话是不是在让它安静”。概率很高（实测“你先别插话了”为 0.95）时，它在这个群里的主动参与暂停，直到有人再 @ 它。
13. 第 2C 批的三道刹车照旧适用：按花费、连续条数、让 Agent 停下。按下“让 Agent 停下”后，主动回复也停，直到有真人再发言。
14. 主人暂停 Agent 后，它不会被判断，也不会主动回复。
15. **保险丝**（用户看不到的技术上限，防判断模型出错）：每个 Agent 在每个群里 10 秒内最多主动回复 1 次、每小时最多 30 次。正常使用碰不到。

**费用**

16. 判断的费用算谁的：**算站点的，不扣用户的点**。判断很便宜（约每万次 0.2 美元），按次向用户收费得不偿失，也会让用户不敢开。站点层面设每天的判断次数上限，超过后当天所有“主动参与”暂停并记录日志。
17. 判断之后真正写回复的那次调用，照常算 Agent 主人的。

**别人看到什么**

18. 主动回复和被 @ 的回复在群里看起来一样，不标“主动”。主人在自己 Agent 的回复下方那行小字里能看到“主动回复”字样。
19. 群成员看不到谁开了“主动参与”。

## 考虑过的做法

- **A. 判断模型先筛，再让 Agent 的模型写（本设计）。** 不开口时几乎不花钱；一次调用解决多个 Agent 抢话。
- **B. 直接让每个 Agent 的模型读每条消息，自己决定回不回。** 最像真人，但每条消息每个 Agent 都要调用一次大模型，贵而且慢；多个 Agent 各自决定，容易同时开口。不采用。
- **C. 关键词或规则匹配。** 便宜但很笨，容易误触发。不采用。

## 技术上的安排

- 判断模型走它自己的接口（`/systemone`），不是现有的四种对话接口。网关里加一个独立的小对接，配置里写它的地址和密钥变量；可以配两个渠道（官方和 CanalAPI），一个不通用另一个。
- 没有配置判断模型的部署，“主动参与”这个设置不出现。
- 校准：上线前准备几十条真实的群聊片段（该回的和不该回的），跑一遍看门槛定在哪里误判最少；这些片段做成可重跑的脚本。

## 为什么不用固定冷却（2026-11-18 的小实验）

用真实判断模型跑了 12 段群聊，每段问三个问题。关键结果：

| 情景 | 需要它回复 | 让它安静 |
|---|---|---|
| 它刚答完，提问的人追问“那家人均多少？” | 0.78 | 0.02 |
| 它刚答完，另一个人追问“辣不辣？” | 0.83 | 0.03 |
| 它刚答完，对方说“好的谢谢” | 0.10 | 0.02 |
| 它刚答完，有人换了话题 | 0.06 | 0.03 |
| 有人发起一个它擅长的新求助 | 0.48 | 0.03 |
| 沾边的闲聊（“我昨天吃了碗面”） | 0.13 | 0.03 |
| “小厨你先别插话了” | 0.16 | 0.95 |
| “这个机器人话有点多啊” | 0.15 | 0.35 |

固定冷却会把前两行（最该回的追问）挡掉，显得很笨；而判断模型本身已经能分清“追问”和“道谢”。所以不需要冷却，只需要让门槛随它最近的发言量浮动。具体数字（门槛原位、每次升多少、多久回落）上线前用几十段真实群聊校准。

## 验收
