# Agent Family 第 1 批设计：真实社交

日期：2026-11-15（第二版，按“消息核心自研”重写）。状态：**用户已于 2026-11-15 批准**。下一步是实施计划；计划经用户确认后才开始实现。

本文写给做实施计划的人。读完应能据此排计划，不需要再回头问用户。标注“我的决定”的条目是撰写者的选择，不是用户确认过的，审阅时请重点看。

## 1. 意图

把用户已认可的 `prototype-v2` 界面，从浏览器内的模拟数据变成真实的多用户产品的第一段：真人之间的账号、好友、私聊、群聊和附件。

为什么先做这一段：后面的个人 Agent、Agent 社交、任务与电脑都建立在“账号、关系、会话、消息、规则”这几样东西上。这一批把它们做成真的，并且从第一天起就由服务端强制，而不是靠界面隐藏按钮。

产品全貌（用户已确认）：所有人都在这一个站上；人和 Agent 都是居民，可以互加好友、私聊、建群；每个 Agent 有一位主人，Agent 参与的对话主人都看得见；Agent 有站内配置的和主人接入的外部 Agent 两种。本批只做真人部分，但数据结构要为后面留好位置。

## 2. 目标、非目标、反目标

**目标**

- 一个账号、一个入口：在我们自己的页面注册、验证邮箱、登录、找回密码。
- 真人加好友（申请、接受、拒绝、撤回、过期、解除）、拉黑与解除。
- 好友之间私聊；好友之间建群、群内收发、加人、退群、移除成员。
- 文字、图片、文件、引用回复、表情、@ 提及；发送失败可重试；未读数；私聊已读状态；会话内搜索和跨会话的全局搜索。
- 刷新、断线重连、换设备登录后历史正确，不丢消息、不重复。
- 所有限制在服务端生效：绕过界面直接调用接口也突破不了。

**非目标（本批不做）**

- Agent 的任何真实能力：创建、模型、回复、讨论、任务、电脑、外部 Agent 接入。任务运行器采用哪个项目尚未决定，计划在第 4 批开始前单独做对比验证。
- 扩员确认与恢复确认流程（属于含 Agent 的会话，第 3 批）。
- 桌面和手机客户端、离线推送、语音视频。
- 跨服务器互通、端到端加密。
- 旧数据迁移。线上现有数据是测试数据，替换时直接清空。
- 替换线上入口。本批只交付到一个独立的验收环境。

**反目标（做成这样就算失败）**

- 界面偏离已认可的布局、配色、密度，或换成了任何现成聊天软件的默认界面。
- 真实构建里还混着模拟数据、模拟回复或“演示状态”入口。
- 任何一条限制只在前端判断。
- 浏览器拿到了别人的凭据，或拿到了能代表别人发言的东西。
- 为了赶进度手写了成熟框架已经提供的基础能力（网络层、会话管理、密码处理、参数校验）。

## 3. 约束

- 已确认的决定：单站；消息核心自研，不使用 Synapse 或 OpenIM；不启用端到端加密；账号以我们的服务为准。依据见 `spikes/base-gate/README.md`，尤其是“第二轮”和其中独立攻击测试列出的 10 个问题。
- 界面基线是 `prototype-v2`，规则见其 `AGENTS.md`。
- `prototype-v2/`、仓库根目录的旧应用、`spikes/` 在本批中保持原样，不修改。`spikes/base-gate/core/` 和 `spikes/base-gate/ui-live/` 是一次性验证代码，可以参考思路，不直接搬用。
- 可以在本机的工作分支上提交。未经用户明确指示，不推送、不部署，不触碰线上。
- 项目自身的开源许可证尚未决定。本批只引入宽松许可证（MIT、Apache-2.0、BSD、ISC 一类）的依赖，不引入 AGPL/GPL 代码。
- 开发机是 Windows 11，本机没有 Docker，有 WSL（Ubuntu）。并发测试用的 Postgres 装在 WSL 里（见第 9 节）。
- 用户不是工程背景。需要用户决定的只应是“用户会看到什么、规则怎么算”，并附具体例子和建议；技术选择由实施者决定并说明。

## 4. 考虑过的做法

**消息这一块用什么**

| 做法 | 取舍 | 结论 |
|---|---|---|
| OpenIM | 在我们测试的版本和配置下，未通过权限隔离相关的测试项（细节未公开，见 `spikes/base-gate/README.md`） | 排除 |
| Synapse＋规则模块 | 消息通道成熟，将来互通有路。但成员名单要存两份；每次写入要回头询问我们的服务；已读、资料、附件、搜索在规则模块管辖之外要另外堵；外部 Agent 接入仍需另做 | 验证可行，未选 |
| 自研消息核心，其余复用 | 账号、关系、成员、消息、规则在同一个数据库里，判断和写入是同一步；附件授权、历史边界、Agent 身份都是原生的；部件少。代价是消息通道的可靠性和安全要自己做对并长期守住，原生端 SDK、推送、互通都没有现成的 | **用户已选** |

**账号以谁为准**：用户已选“以我们的服务为准”。在自研方案里这不再是一个需要协调的问题，账号和消息本来就在同一个服务里。

## 5. 总体结构

```
浏览器（prototype-v2 演进的网页端）
   │  HTTP：登录、好友、会话、消息、附件
   │  长连接：新消息与变更的实时推送
   ▼
AF 服务 ──► Postgres（账号、关系、会话、成员、消息、附件登记）
        └─► 对象存储（附件内容，不对外公开）
```

只有一个后端服务和一个数据库。它是账号、好友、拉黑、会话、成员、消息的唯一权威。

核心做法，本批所有写入都要遵守：**“能不能做”的判断和“做”本身在同一个数据库事务里完成。** 例如发消息：在一个事务里确认发送者是现成员、会话允许发送、双方关系允许，然后分配序号并写入。不存在“先问再写”之间的空档。

### 5.1 代码位置（我的决定）

新建顶层目录 `app/`：

- `app/web/`：网页端
- `app/service/`：AF 服务
- `app/deploy/`：部署描述

### 5.2 技术选择（我的决定）

- AF 服务：TypeScript、Fastify，所有接口的输入用声明式的参数校验，不合规的请求在进入业务逻辑前被拒绝。
- 账号：Better Auth（邮箱＋密码、邮箱验证、找回密码、会话管理）。旧应用已在使用。
- 数据库：Postgres，带版本号的迁移文件。
- 实时推送：WebSocket，使用成熟的库。
- 附件内容：S3 兼容的对象存储，存储桶不公开；登记信息在 Postgres。
- 网页端：沿用原型的 React＋Vite。不引入第三方聊天 SDK。

## 6. 各部分设计

### 6.1 账号与登录

- 注册需要邀请码（我的决定：验收期不开放任意注册；做成配置开关）。注册信息：邮箱、密码、显示名、唯一账号名（界面上的 `@xiaolin`，注册后不可改）。
- 邀请码由管理员用一条命令生成，每个码只能用一次、可设有效期（我的决定：本批不做管理界面）。同样提供一条命令查看测试收件箱里的邮件。为了让用户能做人工检查，实施者在验收环境里预先建好几个已验证的测试账号交给用户，并说明如何自己再注册新账号。
- 注册后需要验证邮箱，验证前不能使用（用户已确认）。
- 找回密码：申请重置、凭邮件链接设置新密码。链接一次有效、限时失效；重置成功后该账号的所有已登录会话全部作废。无论邮箱是否已注册，申请页面给出相同提示。
- 登录、注册、申请重置都要限速，并且响应时间不能让人分辨出账号是否存在。
- 密码规则、会话时长沿用旧应用 `server/auth.ts` 的设置（密码 10 到 128 位，会话 7 天）。提供退出登录；退出后该会话立即失效，已建立的长连接被断开。
- “把邮件发出去”做成可替换的一环。验收环境不真实发信，邮件写入一个只有管理员能读的测试收件箱；上线时由用户选定域名和发信服务商后换成真实发送。本批不选服务商。
- 原型没有的页面，按原型的视觉风格新做：登录、注册、邮箱验证提示、找回密码。

### 6.2 身份模型

后续批次的规则以 `prototype-v2` 的状态代码（`src/state/reducer.js`、`src/state/selectors.js`）、它的 17 条状态测试和 README 为准，没有另外的规则文档。本批据此预留字段，属于尽力而为：第 2、3 批设计时如发现需要调整表结构，以那时的设计为准。

数据库里统一用“主体”表示会话的参与者，类型为真人或 Agent。本批只会产生真人主体。Agent 主体的字段（主人是谁）在表结构里预留，并加上数据库约束：Agent 必须有主人，真人不能有主人。这样第 2、3 批加入 Agent 时不需要改动消息和成员相关的表。

### 6.3 好友与拉黑

按“主体对主体”设计，本批主体只有真人。

- 找陌生人只能通过准确的账号名；不提供对全站用户的模糊搜索和浏览。通讯录页面列出的是自己的好友和待处理的申请，页面上的搜索框只在这份列表里做本地筛选。这与原型的通讯录外观一致，但原型里那份可浏览的名单在真实产品中只包含自己的好友。
- 申请状态：待确认、已建立、已拒绝、已撤回、已过期、已解除。待确认 24 小时后过期，由服务端判定。
- 同一对主体同时只有一条待确认申请。已拉黑对方时不能申请。
- 接受后立即为双方创建私聊。
- 解除好友：私聊保留历史，但不能再发新消息。重新成为好友后继续使用同一个私聊。
- 拉黑：单向记录，不解除好友关系。拉黑后双方的私聊不能发新消息，被拉黑方不能发起申请。解除拉黑后私聊恢复可发（我的决定：真人私聊不走“恢复确认”流程，那是含 Agent 会话的规则）。
- 只要任一方拉黑了另一方，两人就不能把对方加进任何群（我的决定）。
- 被拉黑的一方能看到原因，沿用原型的提示“某某拉黑了某某，只能由对方解除”。
- **拉黑对纯真人群的影响（我的决定，请确认）**：不冻结群。两人仍在同一个群里，彼此消息照常可见。含 Agent 的群在第 3 批按原型规则处理。

### 6.4 会话与成员

- 本批的会话类型：真人私聊、纯真人群。原型没有“纯真人群”类型，本批在界面数据层新增，外观沿用混合群的样式，但不显示任何与 Agent、主人相关的标注。
- 建群：创建者从自己的好友里选至少两人，并填写群名。被选的人直接入群，不需要再确认（我的决定：与常见聊天产品一致；含 Agent 的群另有扩员确认，第 3 批）。群名之后只有创建者能改。
- 加人：任何成员都可以把自己的好友加进群（我的决定）。移除成员：仅创建者。退群：任何人；创建者退群时把创建者身份交给最早入群的现成员；最后一人退出后会话关闭。
- 群人数上限 500，按会话内账号总数计。
- 每条成员记录有角色，本批只有“发言成员”，为第 3 批的“旁观主人”预留。
- 成员资格按“时段”记录：加入时的消息序号、离开时的消息序号。
- **可见范围的固定规则**：一个人只能读到自己**当前这次**加入之后的消息和附件。新成员看不到入群前的内容；退群或被移除后什么都读不到，会话从列表里消失；重新加入后只能看到重新加入之后的内容，之前在群时段和离开期间的都看不到（我的决定：比“能看回以前在群时段”更简单，也不会出现模糊地带）。
- 私聊不适用“退出”：私聊的两个成员始终是成员，解除好友或拉黑只影响能否发送，不影响各自查看已有历史。

### 6.5 消息

- 每个会话内的消息有连续递增的序号，由服务端在写入事务里分配。
- 发送者只取自登录会话，请求里任何表示发送者的字段都被忽略。
- 允许发送的条件，在写入事务里一并判断：

  | 写入 | 允许条件 |
  |---|---|
  | 私聊里发消息 | 双方是好友，且任一方都没有拉黑对方 |
  | 群里发消息 | 发送者是该会话的现成员 |
  | 引用回复 | 被引用的消息是发送者当前看得见的。引用只保存“指向哪条消息”，不保存被引用的文字 |
  | 带附件的消息 | 附件由发送者本人上传到这个会话 |

- 看一条带引用的消息时，被引用的那条如果不在读者当前的可见范围内（例如读者是后来加入的），引用处显示“引用的消息不在你的可见范围内”，不显示原文（我的决定）。
- 断线重试：客户端为每条消息生成一个标识，服务端保证同一发送者在同一会话里用同一标识只会产生一条消息。同一标识出现在另一个会话时按新消息处理，不能悄悄丢弃。
- 消息类型本批为文字和附件，另有服务端产生的系统通知（加入、离开、改群名、关系变化导致不能发送）。消息内容用可扩展的结构保存，为以后的任务卡、授权申请等类型留位置。
- 本批不做消息撤回和编辑（我的决定：原型里没有这两个操作）。
- 已读：记录每个成员在每个会话读到的序号，多设备共享。私聊里显示对方是否已读；群里只用它计算自己的未读数。
- 不能发送的状态：本批只有私聊会进入这种状态，原因是“不再是好友”或“存在拉黑”，由关系状态直接推导，关系恢复即恢复，不需要手动操作。此期间双方的消息和附件上传都被拒绝，系统通知不受限制。数据结构上为第 3 批“会话被冻结并带原因”留出位置，但本批不实现手动冻结与恢复。

### 6.6 同步与实时

- 网页端打开时取一次全量：自己的会话列表、成员、未读数、每个会话最近的若干条消息。之后通过长连接接收新消息和变更。
- 断线重连后，网页端按“每个会话已收到的最后序号”向服务端补齐缺失部分，保证不丢、不重。
- 长连接的鉴权不把长期凭据放在地址里；使用登录会话换取的短时一次性票据，或等效做法。
- 成员被移除、退出登录、会话变为不能发送时，相关的长连接要立刻收到变更；被移除者已打开的连接不能再收到该会话的任何内容。
- 不能泄露与本人无关的信息：同步接口不返回全站范围的计数或游标；对不存在的会话和无权访问的会话给出完全相同的响应。
- 已知并接受的一点：会话内序号是连续的，后加入者能从序号看出入群前大约有多少条消息，但看不到内容（我的决定）。
- 历史翻页：按序号向前取，每次有上限。

### 6.7 附件

- 上传需要是会话现成员且会话可发送。**这个判断要在上传完成、登记入库的那一刻再做一次**，不能只在开始时判断。
- 单个附件上限 50 MB（我的决定），并按账号限制总量和频率，具体数值由实施者定一个保守值。
- 下载只有一条路：向 AF 服务请求某个附件，服务确认“存在一条携带该附件、且请求者当前看得见的消息”才放行。上传了但没有随消息发出的附件，谁都取不到，并定期清理。
- 对象存储不公开。若使用短时签名地址，签发前做上述判断，有效期以分钟计。
- 返回附件时由服务端决定内容类型和下载方式，不采用上传者声称的类型来决定浏览器如何处理：图片类型白名单内的可内联显示，其余一律作为下载。附件与网页不同源，或采取等效措施，防止上传的文件在网页的身份下执行脚本。
- 头像：登录用户都可以看任何用户的头像，单独的接口，不走按消息授权。用户可在设置里上传头像；未上传时使用按账号生成的默认头像（我的决定）。

### 6.8 搜索

- 会话内搜索：先搜已加载到本地的消息；搜不到或想搜更早的记录时，提供“继续向更早的记录搜索”。实现方式由实施者在“浏览器逐页取回本地匹配”和“服务端在本人可见范围内按片段匹配”之间选择；后者在验证中已证明对中文有效。无论哪种，结果只能来自本人当前可见的范围，并显示进度、可随时停止。
- 全局搜索（用户于 2026-11-16 确认放进本批）：在本人当前可见的所有会话里按片段搜索消息文字和文件名，结果按时间倒序分页，每条结果带所属会话和位置。可见范围的判断与会话内搜索完全相同：只包含本人当前这次加入之后的消息，已退出或被移除的会话不出现。界面上放在左上角已有的搜索框里，在联系人和会话的结果之外增加一栏“聊天记录”，点击后打开对应会话并定位到那条消息。
- 两种搜索都只搜消息文字和文件名，不搜文件内部的内容。

### 6.9 网页端

从 `prototype-v2` 复制到 `app/web/` 后改造。

- 用真实数据层替换原型的本地状态和模拟计时器。页面组件、样式、交互细节保持不变。
- 去掉写死的“我”和模块级的人物表，改为从登录身份和服务端数据读取。
- 真实构建中不包含“演示状态”抽屉、模拟回复、模拟附件、重置演示数据。
- 本批尚未接通的入口（我的决定）：导航里的“Agent”保留，页面显示“尚未开放”的空状态，不展示任何模拟 Agent；通讯录只显示真人；聊天里与 Agent、任务、讨论、扩员、恢复有关的界面元素不出现。
- 接通的交互：会话列表与搜索、私聊与群聊、文字、表情、@ 提及（仅当前会话的成员）、引用回复、图片与文件的发送和查看、发送失败与重试、未读数、私聊已读、右侧会话资料面板、群资料页的成员列表、通讯录与好友申请、拉黑、设置里的个人资料与退出登录。
- 原型里没有、本批需要新做的界面：登录、注册、邮箱验证提示、找回密码、建群（放在“新建”菜单里，含选好友和填群名）、群资料页里的直接加人、退群、改群名。由实施者按原型已有的组件和样式来做，不等待另外的设计稿；做完后由用户在浏览器里看过再算通过（我的决定）。
- 不能发送时沿用原型已有的冻结提示样式，文案按实际原因显示；服务端拒绝一次发送时沿用原型已有的“发送失败，未发布”样式。
- 只支持现行版本的桌面浏览器；窄屏布局沿用原型已有的适配，不另做手机专用界面。

### 6.10 部署形态

本批交付到一个独立的验收环境，放在 Railway，与现有线上项目分开：AF 服务（同时提供网页端静态文件）、Postgres、对象存储。

验收环境使用临时地址。将来上线是用最终域名另行部署并清空旧数据，最终域名和发信服务商在那时再定。

批准本设计不等于批准部署。搭建验收环境是实施计划里的一个明确步骤，执行到那一步时要先得到用户同意。线上现有的 Element、Synapse、数据库不动。

## 7. 验收

以下全部通过才算本批完成。除标注“人工”的以外，都应是可重复运行的自动化测试。规则类的测试以普通用户的登录会话直接调用服务端，不经过界面。第 1、5、19 项涉及网页端自身的行为（刷新、换浏览器、断网重连、服务重启后恢复），需要一小套浏览器自动化测试来覆盖。

**正向**

1. 两个新账号各自注册、验证邮箱、登录；其中一个走一遍找回密码后用新密码登录；互加好友；私聊双向收发；刷新后历史完整；换一个浏览器登录后历史完整。
2. 三人建群；群内收发；发送图片和文件，其他成员能打开，内容一致。
3. 引用回复、@ 提及、表情、未读数、私聊已读、会话内搜索和全局搜索（含中文片段、向更早记录搜索、从全局结果跳到对应消息）在两个真实浏览器会话之间表现正确（人工，按原型的交互逐项核对）。
4. 界面与 `prototype-v2` 逐页对照，布局、配色、密度没有偏离；新做的界面由用户看过（人工）。
5. 断开网络一段时间再恢复：期间别人发的消息全部补齐，自己断网时发出的消息重试后只出现一条。

**负向：规则**

6. 非好友不能私聊；解除好友后不能再发；拉黑后双方都不能再发；被拉黑方不能发起申请；存在拉黑的两人不能把对方加进群。
7. 非成员读不到群的消息、单条消息、成员，搜不到内容，收不到推送，发不进去，传不了附件，加不进去；对不存在的会话与无权访问的会话，响应完全相同。
8. 后加入者通过历史、翻页、单条、会话内搜索、全局搜索、全量同步、断线补齐、引用旧消息，都拿不到入群前的内容，也下载不到入群前的附件；入群后的可以。
9. 被移除或退群的人读不到任何内容，全局搜索里也不再出现该会话的消息，已打开的长连接不再收到该会话的推送；重新加入后只能看到重新加入之后的内容。
10. 普通成员不能移除别人、不能改群名、不能改任何人的角色；不是自己好友的人加不进群。
11. 不带登录会话、用别的会话里的附件编号、上传后未发出的附件、对象存储的直接地址，都拿不到附件内容。
12. 请求里伪造发送者字段无效；一个账号不能读取或修改另一个账号的好友列表、申请、拉黑记录、个人资料、已读位置。
13. 申请到期后不能再被接受；重复申请不产生第二条记录；同一标识的消息重发不产生第二条，换一个会话使用同一标识会正常产生新消息。
14. 未验证邮箱的账号不能使用；重置链接用过一次或过期后失效；重置密码后旧的登录会话全部不能再用；退出登录后该会话的接口调用和长连接都失效；对未注册邮箱申请重置与对已注册邮箱申请，页面表现和响应时间不可区分；邀请码用过一次后失效。

**负向：健壮性与并发**

15. 对所有接口发送畸形输入（错误类型、超长、负数、非数字、空请求体、畸形地址、不合规的长连接数据帧），服务不崩溃，返回 4xx 而不是 5xx。
16. 在真实 Postgres 上并发测试：解除好友、拉黑、移除成员与发消息同时发生时，被接受的消息数与实际入库数一致，生效之后的发送一律被拒；上传进行到一半时失去资格，上传不被接受；同一个人被同时多次加入只产生一条成员记录。
17. 登录、注册、申请重置有限速；超出后被拒绝且不影响其他账号。

**独立攻击测试**

18. 实现完成后，由一位没有参与实现的审查者拿到代码和运行中的服务，专门尝试突破第 6 到 17 项对应的规则，并自由发挥。发现的问题逐条修复并补成自动化测试，直到一轮下来没有新的可利用问题。`spikes/base-gate/README.md` 里对验证版列出的 10 个问题，凡是适用于本批范围的，每一个都要有对应的测试。不适用的两条：主人退出后 Agent 仍留在会话，记入第 3 批的验收；冻结期间退出仍写入系统消息，本批只有私聊会进入不能发送的状态而私聊不能退出，同样留到第 3 批。

**运行**

19. 验收环境可以按文档从零重建；服务重启后，已登录的网页端能自动恢复，历史不丢。
20. 数据库和附件可以备份并恢复到一个新环境，恢复后第 1、2 项仍然成立。

每项验收要分别记录：代码状态、测试覆盖到什么、是否已部署、还有哪些限制。
